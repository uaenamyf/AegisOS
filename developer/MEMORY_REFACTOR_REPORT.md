## 1. 赛题要求（原文 + 解读）

### 1.1 题目定位
> **题目编号 XH-202631**：面向超长程复杂任务的动态异构群体智能架构与深度协同推理技术（荣耀终端命题）。

### 1.2 与记忆直接相关的核心要求（原文）

> **目标介绍（原文）**：“重点攻克在超长周期下的**上下文连续性保持**、神经符号协同推理与低熵通信难题。”

> **答题要求 a（原文，评分核心项）**：
> “系统须在跨越多轮决策流转的长程任务中，克服**注意力稀释**与**记忆坍缩**问题。设计**分布式记忆架构**与**上下文压缩唤醒机制**，确保关键任务信息、中间决策结果与全局目标在长链推理中**不丢失、不漂移**，**不依赖单一模型的长窗口无损外推**。”

> **答题要求 b（精神）**：要求体系具备**全局动态任务编排**与**自适应网络拓扑流转**，围绕“多智能体协同”组织，而记忆是支撑“超长周期连续性”的底座。

### 1.3 评分细则里的记忆相关点
| 评分项 | 分值档 | 相关原文要点 |
|---|---|---|
| 完整性·闭环能力 | 7-10 分 | 数千步任务中无明显“过程遗忘”或“规划幻觉” |
| 创新·底层突破 | 高 | 长上下文管理、克服注意力衰减的原创性突破 |
| 跨领域泛化 | 9-10 分 | 跨领域长程任务（不止单一场景） |
| 交付物 | — | 接受动态注入的**节点失效并无人工干预恢复** |

### 1.4 一句话翻译成工程语言
赛题要的其实是三件事，缺一不可：

1. **上下文压缩唤醒机制** —— 长任务里记忆会被“压成摘要 + 按需唤回”，而不是一股脑全喂给模型。
2. **分布式记忆架构** —— 记忆分层（短期/长期/语义/向量）+ 可扩展后端，不是单一进程里的一个 dict。
3. **容错恢复** —— 节点挂了能靠记忆里的检查点/快照恢复，不用人管。

## 3. 问题清单（每条带证据 + 影响）

### 🔴 P0 级

**问题 1：记忆“唤醒”半闭环——只有压缩，没有唤醒**
- 赛题原话要“压缩**唤醒**机制”，现在是压缩了、也注入了，但“推理前从记忆里召回相关经验再喂模型”这半边没接。
- 证据：`store.recall()` 的全部调用都在 `tests/` 里（test_*.py），`cyber_orchestrator.py` 生产代码只有 `write` + `compress`,没有推理前 `recall`。
- 影响：演示“它记得历史经验并用起来了”时,评委追问“怎么唤醒的”,答不上。

**问题 2：两个 MemoryStore 孤岛,记忆不同源**
- 证据：`backend/core/composition.py:119` 构造 `CyberDefenseService` 时**没传 memory**,而 service 内部 `_memory = memory or MemoryStore()`（`cyber_defense_service.py:67`）自建一个;REST `/memory` 用的是 composition 里另一个实例。
- 影响：前端读到的记忆 ≠ 演练产生的记忆。功能上不崩,但“记忆是统一的”这个说法站不住。

**问题 3：向量/语义检索是“休眠通道”**
- 证据：全项目 `embedding=` 只出现在测试文件;没有任何生产代码生成 embedding。RRF 三通道实际只有关键词+图两通道在转。
- 影响：扣“核心算法突破”的分。

### 🟠 P1 级

**问题 4：记忆不持久化,跨重启全丢**
- 证据：MemoryStore 全内存 dict;`data/aegisos.db` 只存 session/task,不存记忆。“慢思考 GTM-3 近 2000 后状态”这种对记忆窗口的要求,重启就没了。
- 影响：演示要一口气跑完;评委增删会话/重启发问就露馅。“分布式记忆架构”名不副实。

**问题 5：检查点/快照/归档钩子没接线**
- 证据：`checkpoint_cycle/archive_cycle/snapshot_cycle` 定义在 `memory_store.py:258-296`,测试在 test_checkpoint/test_snapshot,但 `cyber_orchestrator.py` **零调用**。
- 影响：交付物要求“动态注入节点失效并无人工干预恢复”,现在演示不出恢复。

**问题 6：普通任务链路无记忆**
- 证据：`backend/services/task_service.py` 构造只接 `runtime`,不接记忆。Chat 提交的任务没有记忆闭环。
- 影响：记忆覆盖面=单一攻防场景,而评分 9-10 档要求“跨领域长程任务”。

### 🟡 P2 级（体验/工程细节）

**问题 7：前端没有“记忆可视化”入口**
- 现状：`memoryApi` 有但没被视图消费;Replay 里有 `memory.update` 事件类型但无落地界面。
- 影响：评委看不到“记忆在长任务里的作用”,记忆能力=黑盒。

## 4. 改造方案总体设计

### 4.1 核心思路（一句话）
> **把“只有压缩的半闭环”补成“写→压缩→唤醒→注入”的完整认知循环，并把记忆统一成单例、落到盘上、接到普通任务、最后可视化出来。**

### 4.2 目标架构（改完后长这样）

```
                     ┌─────────────────────────────────────────────┐
                     │               MemoryStore (单例)             │
                     │  ┌──────────┐ ┌──────────┐ ┌──────────────┐  │
  演练编排器 ────────▶│ │ 短期工作记忆 │ │ 长期情景记忆 │ │ 语义/向量知识库 │ │
  (写→压缩→唤醒)      │  └──────────┘ └──────────┘ └──────────────┘  │
                     │         │         │                          │
  普通 Task 服务 ────▶│         ▼         ▼         ▼               │
  (接入同一实例)       │  压缩器(compactor) 检索引擎(RRF) embedding器 │
                     └────────┬────────────────────────────┬───────┘
                              │ 落盘(SQLite/JSON)           │ 可视化
                        ┌─────▼─────┐              ┌───────▼───────┐
                        │持久化层     │              │ REST /memory  │
                        │(跨重启保留) │              │ + 前端 Memory  │
                        └───────────┘              │  视图/回放     │
                                                    └──────────────┘
```

### 4.3 短期记忆 vs 长期记忆的设计（赛题视角）

| | 短期记忆 (working) | 长期记忆 (episodic/semantic) |
|---|---|---|
| 存什么 | 当前任务的中间状态、本轮决策、最近几步 | 跨任务/跨会话的经验、ATT&CK/CVE 知识、历史结论 |
| 生命周期 | 任务结束/会话结束即降级或清理 | 长期保留,可跨会话复用 |
| 访问方式 | 随上下文直接注入 | **按需 recall**(检索唤醒),不常驻 |
| 规模控制 | 靠 compactor 按 token 预算压缩 | 靠检索 top-k 截断 + 归档降级 |
| 这正是赛题要的 | “上下文连续性保持” | “记忆保持 + 唤醒复用” |

改造的关键动作，就是把**短期记忆的“压缩”**和**长期记忆的“唤醒”**接成一条真实链路。

## 5. 具体改造步骤（按优先级）

### 步骤 ①（P0）统一 MemoryStore 单例 + 接通唤醒
- **改什么**：
  - `composition.py` 传入同一个 `MemoryStore` 给 `CyberDefenseService` 和 `TaskService`。
  - 编排器每轮**推理前**调 `memory.recall(prompt关键词)` 召回相关历史,连同 `prior_rounds_summary` 一起注入下一轮。
- **为什么先做**：动最少、演示价值最大,把“压缩唤醒”题眼补全。
- **验证**：单测断言行 `recall` 被调用;跑演练看下一轮 prompt 里真的多出召回片段。

### 步骤 ②（P0）激活向量通道
- **改什么**：写一个轻量 embedding 模块（bge-small 级别,优先国产/离线）,任务产出和记忆包写入时生成向量;RRF 三通道真正三通道。
- **为什么**：扣“底层算法突破”分,三通道名实相符。
- **风险**：引入模型依赖;降级方案=先用离线规则向量(如 TF-IDF)兜底,不阻塞主流程。

### 步骤 ③（P1）记忆持久化
- **改什么**：给 MemoryStore 加一个可插拔 `persistence` 后端,默认 SQLite(复用 `data/aegisos.db` 或新表),启动时加载、写时落盘。
- **为什么**：解决“重启全丢”,呼应“分布式/可扩展”的措辞。
- **验证**：重启进程后重跑链路,记忆仍在。

### 步骤 ④（P1）接线检查点/快照 → 容错恢复
- **改什么**：轮到演练循环调 `checkpoint_cycle`,保存 state;编排器检测到异常时 `snapshot.restore()` 从最近检查点恢复。
- **为什么**：直接命中交付物“节点失效无人工恢复”,是演示叙事的关键一幕。
- **注意**：恢复要有“注入故障”的演示剧本,否则评委看不到。

### 步骤 ⑤（P2）普通任务接入记忆 + 前端可视化
- **后端**：TaskService 挂到同一 MemoryStore,任务关键中间态写入短期记忆。
- **前端**：新增/增强记忆视图——展示记忆分层(短期/长期/知识库)、最近写入轨迹、回放里的记忆事件。改 `memory.ts` 增加列表/检索端点;`views/monitor` 或 `views/replay` 加记忆面板。

## 6. 改了记忆后,相关模块怎么联动调整

### 6.1 后端接口
| 现有 | 调整 |
|---|---|
| `GET/POST /memory/{session_id}` | 保留,语义不变 |
| （新增）`GET /memory/{session_id}/recall?q=...` | 暴露“唤醒检索”,供前端可视化 |
| （新增）`GET /memory/{session_id}/trace` | 记忆写入轨迹,供 Monitor/Replay 展示 |
| `GET /drill/{id}/report` | 报告里已含 `memory_trace`,可扩展为前端可点的事件流 |

### 6.2 前端 UI
| 视图 | 现状 | 调整 |
|---|---|---|
| Chat | 发任务,无记忆感知 | 任务执行时可选展示“本任务记得的历史” |
| Canvas | 任务 DAG | 节点详情可展示该步写入的记忆包/压缩摘要 |
| Graph | 协作拓扑 | 可按记忆类型着色(短期/长期/知识库),展示记忆-任务边 |
| Monitor | 运行监控 | 新增“记忆状态”面板:分层占用、最近写入、压缩比 |
| Replay | 事件回放 | 接入 `memory.update` 事件,时间线上标出“记忆写入/压缩/唤醒”时刻 |

前端改动原则：**记忆能力优先以“可视化面板”形式出现,不强行塞进每个视图**,最自然落点是 Replay(时间线)和 Monitor(状态面板)。

### 6.3 编排器 / 服务层
- `cyber_orchestrator.py`：加推理前 recall 注入(与现有 `prior_rounds_summary` 并存)。
- `composition.py`：统一注入单例 MemoryStore + persistence 后端。
- `task_service.py`：挂载记忆,写短期记忆。
- `drill_report.py`：报告里补充“唤醒命中”“压缩比”等可视化指标。
